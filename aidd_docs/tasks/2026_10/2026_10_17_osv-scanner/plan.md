# Plan: Failles de Vigie lui-même, osv-scanner en CI (F8)

## Overview

| Field      | Value |
| ---------- | ----- |
| **Goal**   | Savoir, sans y penser, qu'une dépendance de Vigie (veilleur, console Tauri, module PrestaShop) a une faille publiée, et empêcher qu'elle passe inaperçue sur `main` |
| **Source** | Issue GitHub #22 ; `.github/workflows/garde-fous.yml` (modèle gitleaks : version + SHA-256 vérifiée) ; `.github/workflows/console-release.yml` (cibles publiées : Windows, Android) ; lockfiles `vigie/Cargo.lock`, `vigie/app/src-tauri/Cargo.lock`, `vigie/app/pnpm-lock.yaml`, `composer.lock` ; relevé local du 2026-10-17 (osv-scanner 2.6.0 et 2.7.0, bases OSV hors ligne) |

## Decisions

| Decision | Why |
| -------- | --- |
| **osv-scanner 2.6.0** (`google/osv-scanner`, Apache-2.0), asset `osv-scanner_linux_amd64` (binaire nu, pas d'archive), SHA-256 `ca69b3d3cd08f889a49dc0a383122f71cc528b83803671df5fd874d97485b108` lue dans `osv-scanner_SHA256SUMS` de la release et recalculée sur le binaire téléchargé le 2026-10-17 (construit le 2026-09-14). 2.7.0 (construite le 2026-10-12) est écartée. Installation calquée sur gitleaks : `env` `OSV_SCANNER_VERSION` / `OSV_SCANNER_SHA256`, `curl -sSfL -o osv-scanner`, `sha256sum -c -`, `chmod +x` ; binaire téléchargé à chaque run, **jamais mis en cache** | Le dépôt n'a pas de règle d'âge, mais une release de cinq jours n'a pas eu le temps d'être signalée si elle était compromise ; 2.6.0 a plus de 14 jours et lit déjà RUSTSEC-2026-0253 (essai local), elle détecte et filtre exactement comme 2.7.0. Sans cache, la somme est vérifiée sur ce qui s'exécute |
| **Provenance SLSA** : la release v2.6.0 publie `multiple.intoto.jsonl`. Au moment de l'épinglage, vérification locale avec `slsa-verifier verify-artifact osv-scanner_linux_amd64 --provenance-path multiple.intoto.jsonl --source-uri github.com/google/osv-scanner --source-tag v2.6.0` (slsa-verifier lui-même vérifié par sa somme) ; sortie masquée consignée dans la PR et mentionnée dans `decisions.md`. Pas en CI : la somme épinglée suffit une fois la provenance vérifiée | La somme dit « même binaire qu'à l'épinglage », la provenance dit « construit par le dépôt google/osv-scanner depuis ce tag » ; une seule vérification suffit pour un binaire figé par sa somme |
| Nouveau job `deps` (« osv-scanner ») dans `garde-fous.yml`, à côté de `secrets` et `tls-deps`, `ubuntu-24.04`, `timeout-minutes: 10`, `actions/checkout` épinglé par SHA (`11d5960…` v4.4.0, déjà utilisé), `permissions: contents: read` (celles du workflow, inchangées, et rappelées au niveau du job) | L'issue le demande ; garde-fous tourne sans filtre de chemin, donc sur tout changement de lockfile, console comprise ; un appel réseau pendu ne bloque pas un runner six heures |
| Commande : `./osv-scanner scan source --lockfile=vigie/Cargo.lock --lockfile=vigie/app/src-tauri/Cargo.lock --lockfile=vigie/app/pnpm-lock.yaml --lockfile=composer.lock`, **sans `--config`**. Lockfiles nommés, pas `--recursive` ; base OSV en ligne (`api.osv.dev`, joignable depuis les runners) ; pas de `--call-analysis` | Liste explicite : un lockfile absent ou renommé sort en 127 au lieu d'être sauté en silence (vérifié). L'analyse d'appels Rust exécute les scripts de build : hors de question dans un garde-fou |
| **Fail-closed sur tout code non nul** : 1 = faille, 127 = erreur (vérifié : `api.osv.dev` injoignable → 127, « max retries exceeded »), 128 = aucun paquet. Aucune tolérance de sévérité ; un « non maintenu » RustSec compte comme une faille | Exigence de l'issue (« toute faille fait échouer le job ») ; une panne réseau ne doit pas passer pour « aucune faille » |
| Déclencheurs du workflow : `push`, `pull_request`, `workflow_dispatch` existants, plus `schedule: - cron: "17 5 * * 1"` (lundi 05:17 UTC). Le cron s'applique à tout le workflow (gitleaks et `tls-deps` repassent aussi, coût négligeable) | Une faille se publie sans qu'aucun commit ne change ; minute décalée de l'heure pleine pour éviter la file d'attente des crons ; pas de `if:` par job à maintenir |
| **Exceptions au plus près du lockfile** : `vigie/app/osv-scanner.toml` (braces, postcss-selector-parser) et `vigie/app/src-tauri/osv-scanner.toml` (glib, proc-macro-error) ; aucun fichier à la racine ni dans `vigie/`. Chaque entrée `[[IgnoredVulns]]` porte `id`, `ignoreUntil` (date TOML) et `reason` (origine, pourquoi non exploitable chez nous, condition de levée) | Vérifié avec 2.6.0 et 2.7.0 : chaque lockfile ne lit que le fichier de son dossier, sans remontée vers le parent ; une exception de la console ne peut pas masquer la même faille dans le veilleur ou le module |
| **Règle des exceptions vérifiée par script** : `vigie/scripts/check-osv-exceptions.py` (`python3 -I`, `tomllib`, bibliothèque standard seule ; Python 3.12 de `ubuntu-24.04`) lancé dans le job `deps` **avant** le scan, sur tous les `osv-scanner.toml` suivis par git (`git ls-files ':(glob)**/osv-scanner.toml'`). Échec si une entrée `[[IgnoredVulns]]` n'a pas d'`id` non vide, a une `reason` absente ou vide (espaces seuls compris), n'a pas d'`ignoreUntil`, a un `ignoreUntil` qui n'est pas une date TOML, ou une échéance à plus de **92 jours** de la date UTC du run ; échec aussi sur toute clé de premier niveau autre que `IgnoredVulns` (dont `PackageOverrides`, qui ignore un paquet entier sans échéance) et sur un TOML illisible. Message par entrée fautive (fichier, id, motif), sortie 1 | osv-scanner accepte une entrée sans `ignoreUntil` ou à 2099 : sans contrôle, la règle « datée, motivée, ≤ 3 mois » ne tient qu'à la relecture. 92 jours = trois mois calendaires au plus long ; le cron hebdomadaire rattrape une échéance qui glisse hors de la fenêtre |
| **Remédier avant d'excepter** : `rqrr` passe de `0.10` à `0.11` dans `[dev-dependencies]` de `vigie/Cargo.toml` (`lru` ≥ 0.18.2), `tests/cli.rs` adapté si l'API change | Un correctif existe ; aucune exception pour ce qui se corrige |
| **Exceptions initiales, échéance au plus tard 2027-01-17** (≤ 92 jours de la date d'implémentation). Raisons : **`GHSA-wrw7-89jp-8q8g`** (glib) : « pile gtk3 de tauri, compilée seulement pour Linux desktop ; aucun livrable Linux (release Windows et Android uniquement, console-release.yml) ; lever si une cible Linux est publiée ou si tauri quitte gtk-rs 0.18 ». **`RUSTSEC-2024-0370`** (proc-macro-error) : macro de compilation de la même pile gtk3, aucun code à l'exécution, aucun livrable Linux ; lever aux mêmes conditions que glib. **`GHSA-vfj7-8cjw-p6xm`** (braces) et **`GHSA-rj75-hqrm-r3gf`** (postcss-selector-parser 6) : outils de build de la console (devDependencies, tailwind 3, chokidar), motifs et sélecteurs écrits par nous, absents du `dist` embarqué ; lever si un correctif amont est publié, au passage à tailwind 4 (issue à ouvrir si l'échéance arrive sans correctif), **ou si l'un d'eux entre dans `dependencies`** | Pas de correctif amont atteignable sans migration ; aucune de ces dépendances n'est dans un livrable publié ni dans le veilleur du VPS ; chaque raison dit quand elle cesse d'être vraie |
| **composer.lock régénéré** (`composer update --no-install`, d'après `composer.json` : 0 paquet) et toujours scanné ; une étape `composer validate --no-check-publish` (composer est présent sur `ubuntu-24.04`) fait échouer le job si le lock redevient périmé : vérifié sur le lock actuel, sortie 2 sans `--strict`, `--strict` inutile. Le module PrestaShop n'a aucune dépendance Composer à l'exécution (`require` : `php` seul) | Scanner un lock qui ne reflète pas `composer.json` ne prouve rien ; le lock vide reste le point d'entrée d'une future dépendance (0 paquet dans un lockfile parmi d'autres : pas d'erreur 128, vérifié) |
| **cargo-deny écarté pour l'instant** : osv-scanner lit déjà la base RustSec (identifiants `RUSTSEC-*`, « non maintenu » compris) ; les crates TLS interdites restent gardées par `check-tls-deps.sh` ; licences et sources de crates ne sont pas demandées. Réévaluer si une politique de licences devient nécessaire | Un second binaire épinglé pour la même base d'avis ; pas de besoin exprimé au-delà |
| **Preuves** : (1) le premier commit de la branche ajoute le job **sans** `osv-scanner.toml` ni remédiation → run rouge sur les 5 failles du relevé ; (2) après fusion, branche jetable `test/osv-detecte` : un commit remet `rqrr = "0.10"` → rouge sur RUSTSEC-2026-0253 ; un second commit (rqrr rétabli) passe l'échéance glib à une date passée → le script d'exceptions la laisse passer (échéance passée, pas trop lointaine) et le scan est rouge sur glib : preuve d'expiration en CI ; (3) essais négatifs du script en CI sur la même branche (entrée sans `ignoreUntil`, échéance à +93 jours) → rouges. Liens des runs consignés dans la PR ; branche supprimée, jamais fusionnée | L'issue demande la preuve qu'une version vulnérable épinglée fait échouer le job ; les failles réelles la donnent sans rien inventer, et l'expiration se prouve sur le runner, pas seulement en local |
| Documentation : section « Dépendances (issue #22) » de `vigie/docs/decisions.md` (décisions datées du jour d'implémentation : version 2.6.0 et pourquoi pas 2.7.0, provenance vérifiée, exceptions au plus près avec la raison glib mot pour mot) avec la marche à suivre quand le job est rouge : lire la faille, mettre à jour la dépendance, sinon exception motivée en PR dans le `osv-scanner.toml` du dossier du lockfile, échéance ≤ 92 jours (le script la refuse sinon) ; retirer une exception signalée « unused » ; rouge en 127 = relancer, jamais excepter ; reproduire en local avec les mêmes commandes (script puis scan). Ligne de CHANGELOG après fusion, comme les issues précédentes | L'issue demande la marche à suivre ; elle sert à celui qui reçoit l'e-mail d'échec du cron |
| Échec du cron visible : GitHub notifie l'auteur du dernier changement du cron ; un dépôt public sans activité 60 jours voit ses crons désactivés, ce qui est noté dans la marche à suivre (réactiver depuis l'onglet Actions) | Une exécution hebdomadaire qui s'arrête sans bruit ne vaut pas mieux qu'aucune exécution |

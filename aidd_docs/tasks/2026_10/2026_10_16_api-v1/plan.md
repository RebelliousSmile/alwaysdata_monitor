## Decisions

| Decision | Why |
| -------- | --- |
| **Pas de mTLS** : `serve` écoute sur `127.0.0.1:8080` et Caddy l'expose en TLS (Let's Encrypt) ; l'API est authentifiée par un jeton d'appareil de 32 octets aléatoires, conservé en SHA-256, comparé en temps constant (`device::ct_eq`), révocable un par un. Le stockage du jeton côté client relève de #12 (Credential Manager sous Windows, stockage privé sous Android) | Un téléphone hors du VPS doit joindre l'API ; un certificat client par appareil sous Android et Windows coûte plus qu'il n'apporte face à un jeton aléatoire révocable. L'issue admet l'une ou l'autre voie |
| **Limite de débit en mémoire de `serve`**, deux tables distinctes : (1) par appareil authentifié (120 appels par minute, rafale 30), bornée par le nombre d'appareils, jamais évincée ; appliquée après l'authentification et **avant** `touch_seen` ; (2) par IP cliente (IPv4 entière, IPv6 sur son /64) : `/api/v1/pair` y passe **avant** traitement (10 par minute) ; pour les autres routes, une requête avec Bearer est authentifiée d'abord et le seau d'IP ne sert qu'à changer un 401 en 429 — un seau d'IP vide ne bloque **jamais** une requête à jeton valide (NAT, CGNAT partagé avec un attaquant). Table d'IP bornée à 4 096 clés ; seul un seau plein (équivalent à une clé absente) est évincé ; table pleine de seaux entamés → refus de ce qui précède l'authentification (fermé). Horloge `Clock::monotonic`. 429 au format uniforme avec `Retry-After`. **IP cliente** : `serve` passe à `into_make_service_with_connect_info::<SocketAddr>()` (tests : `MockConnectInfo`) ; pair sur la boucle locale (`127.0.0.1` ou `::1`, Caddy) → dernière valeur de `X-Forwarded-For` (Caddy remplace l'en-tête sans `trusted_proxies`) ; sinon l'adresse du pair | Freine le forçage des codes et un appareil emballé, sans verrouiller un utilisateur légitime ni se laisser vider par arrosage d'adresses |
| **Journal des appels** : une ligne par appel de `/api/v1` sur la sortie de `serve` (journald) : request_id, appareil (id posé en extension par l'extracteur) ou `-`, méthode, gabarit de route (`MatchedPath`, jamais le chemin brut ni la query), statut, durée en ms. Les 429 d'une même IP sont regroupés (une ligne par minute avec un compteur). Jamais de jeton, de code d'appairage ni d'en-tête | Traçabilité exigée par l'issue, sans données sensibles ni noyade de journald sous attaque |
| **En-têtes stricts** sur toute réponse de `/api/v1`, corps d'erreur compris (couche qui enveloppe celle de `request_id`) : `Content-Type: application/json` quand il y a un corps, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, aucun en-tête CORS ; `OPTIONS` → 404 uniforme (déjà vrai, test). **415 seulement pour un `POST` qui porte un corps** (`Content-Length` > 0 ou `Transfer-Encoding`) d'un type autre que `application/json` ; `ack` sans corps ni `Content-Type` reste accepté (console 0.1.1), un corps annoncé sur `ack` → 415 d'après les en-têtes, sans lire le corps ; un JSON illisible sur `pair` garde son 401 (pas d'oracle) | La console appelle depuis Rust : aucun navigateur à autoriser ; pas de CSRF par formulaire ; aucune requête de la console 0.1.1 ne change de réponse |
| **Liste blanche des DTO vérifiée par instantané** : un test enregistre l'ensemble des chemins de clés JSON de chaque route (`tests/fixtures/api-keys.json`) sur une base peuplée ; toute clé nouvelle fait échouer le test jusqu'à relecture et mise à jour de l'instantané. En plus, recherche de valeurs semées en clair : jeton et code d'appairage (et leurs empreintes en hex et base64), clé publique d'agent (hex et base64), signatures de commandes, contenu de `password_file`. `facts` et `observed` (objets plats bornés par `protocole-agent.md`) sont exclus nommément de l'instantané | Une régression qui sérialiserait une struct du store, ou ajouterait un champ, se voit en CI |
| **Champs issus des logs** : type `LogText` dont le seul constructeur assainit (caractères de contrôle C0, C1, DEL, U+2028/2029 et contrôles bidi → U+FFFD ; troncature UA 512, chemin 512 caractères) ; utilisé par tout champ de DTO d'origine log, **y compris le `detail` des incidents `logs`** (déjà assaini à l'écriture par #8). Tout chemin est servi sans query string, tout referer réduit à son origine. L'échappement HTML est imposé à la console dès cette issue : `vue/no-v-html` en erreur dans `vigie/app/eslint.config.js`, vérifié par le CI de la console | Le JSON échappe les guillemets ; il reste l'injection de terminal et de journal, le texte bidi trompeur, et les jetons dans les URL |
| **Données personnelles de `/logs/ips`** : liste blanche ip, score (entier), niveau, raisons (codes d'énumération), classe ; ni UA, ni chemin ; seulement les niveaux moyen et élevé ; rien au-delà de 48 h : `/logs/ips` filtre `generated_at ≥ now − 48 h` et #8 purge `log_verdicts` à 48 h. Les lignes regroupées de 429 citent l'IP dans journald (rétention de journald du VPS, écrite dans `hebergement.md`). Décision RGPD consignée dans `decisions.md`, section #5 | L'exploitant a besoin de l'IP pour décider (#13) ; le reste du profil n'est pas nécessaire |
| **Pagination par clé** de toute liste qui croît, `limit` 1..100 (défaut 50 ; hors bornes → 400), `cursor` opaque base64url borné à 256 caractères avant décodage ; réponse `{…, "items": […], "next_cursor": … \| null}` ; curseur illisible → 400 `bad_request`. Incidents clos : `ORDER BY closed_at DESC, id DESC LIMIT n+1` en SQL, index `(site, closed_at, id)` ; un incident clos pendant le parcours apparaît avant la page 1 et n'est pas revu (documenté et testé). Verdicts d'IP : **instantané** d'analyse persisté par #8 (`log_analysis`, `log_verdicts` indexé `(site, generated_at, score DESC, ip)`) ; le curseur porte `generated_at` ; instantané purgé (#8 garde 15 min d'instantanés et n'en crée qu'après un repli) → 409 `cursor_expired` (code d'erreur propre, distinct de `conflict`), le client reprend au début. Les listes bornées par la configuration (sites, contrôles d'un site) ne se paginent pas ; `config.toml` refuse plus de 200 sites (vérifier la configuration du VPS avant de déployer) | Exigence de l'issue ; pas de doublon ni de trou entre deux analyses |
| Compatibilité : la console 0.1.1 lit `incidents` dans `GET /api/v1/sites/{id}/incidents` ; la réponse garde `incidents`, qui devient **la première page** (50 derniers incidents clos, au lieu de tous ceux des 30 jours : changement documenté dans `api-console.md`), et ajoute `next_cursor` (le client n'a pas de `deny_unknown_fields`). 429, 415, 400 et 409 s'affichent en 0.1.1 comme « le veilleur a répondu N » | Pas de mise à jour forcée des appareils appairés |
| **Lecture de l'analyse** : `GET /api/v1/sites/{id}/logs` rend l'instantané de #8 (heure de référence, `generated_at`, charge par heure sur 24 h, robots vus avec métadonnées, dépassements de règles) ; site avec source mais sans analyse encore → 200 `{"analysis": null}` ; site sans source → 404 uniforme. `GET /api/v1/sites/{id}/logs/ips` : verdicts paginés. La phase 2 dépend de #8 phase 3 fusionnée | Exigence « logs » de l'issue ; l'exploitant voit ce que #13 proposera |
| Écriture : seul l'acquittement existe ; toute route d'écriture future passe par les garde-fous de #10 (commande explicite, aperçu, `--apply`) et n'est pas dans cette issue | Exigence de l'issue (« écriture ensuite ») |

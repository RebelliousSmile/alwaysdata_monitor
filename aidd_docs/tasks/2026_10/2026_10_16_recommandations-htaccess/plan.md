## Decisions

| Decision | Why |
| -------- | --- |
| Séparer l'**analyse** (déterministe : `Analysis` de #8 → `Vec<Proposal>`, testée par cas) de la **génération** de texte (`Proposal` → bloc `.htaccess`), testée par fichiers de référence (golden files) | Exigence de l'issue ; le texte est la partie fragile |
| Gradation : un robot qui respecte robots.txt (`honours_robots`) → proposition robots.txt seulement ; un robot qui ne le respecte pas, de classe non protégée → règle d'UA ; une IP → règle d'IP seulement si son score propre est élevé, que son reverse DNS, résolu au moment de proposer, la classe hébergeur, et jamais pour une IP d'une classe protégée ni d'un site `behind_proxy` ; jamais rien contre `SearchEngine`, `OtherEngine`, `SocialPreview`, `Browser`, `AiUser`, ni un jeton robots-only (Google-Extended) en règle d'UA | Garde-fous de l'issue et protections décidées dans #8 |
| Une règle d'IP porte son expiration dans Apache lui-même : `RewriteCond %{TIME} <AAAAMMJJhhmmss` (24 h par défaut), l'IP vient de `Entry.ip` (champ client), jamais d'un en-tête | TTL exigé sans écriture automatique au moment de l'expiration ; jamais d'IP tirée de `X-Forwarded-For` |
| robots.txt reste une **proposition à appliquer à la main** (texte affiché par la CLI) : la liste fermée des commandes ne s'étend pas à robots.txt dans cette issue | Plus petite surface ; robots.txt n'exécute rien |
| Le bloc est délimité par deux lignes exactes `# BEGIN vigie` et `# END vigie` (au plus une paire dans le fichier, localisée par opérations de chaînes, jamais par regex) et sa **grammaire se valide par groupes**, par le veilleur à la génération **et par l'agent** avant toute écriture : `RewriteEngine On` une fois en tête, puis des groupes ; un groupe = des `RewriteCond` d'une seule sorte (UA : chaque ligne `[NC,OR]` sauf la dernière `[NC]` ; ou IP : une seule ligne), puis **exactement une** `RewriteCond %{TIME} <AAAAMMJJhhmmss`, puis exactement une `RewriteRule ^ - [F,L]`. Lignes de commentaire `# ` en ASCII imprimable `[ -~]`, sans `\`, sans `BEGIN`/`END`, en colonne 0. Fins de ligne LF seules ; aucun CR, tabulation, NUL ni ligne finissant par `\` (continuation Apache) ; 200 lignes et 16 Kio au plus. Toute autre ligne (`php_value`, `php_flag`, `AddHandler`, `SetHandler`, `AddType`, `Action`, `Include`, `auto_prepend_file`, `allow_url_include`, `Options`, `<Files>`…) fait refuser le bloc entier | Un `.htaccess` libre donne l'exécution de code ; la validation doit tenir même si le veilleur est compromis ; une condition `[OR]` mal chaînée ou une continuation de ligne changerait le sens du bloc |
| **Littéral d'UA = expression régulière** pour Apache : le littéral source n'admet que `[A-Za-z0-9 _/.+-]{3,64}` et s'écrit échappé (`.` → `\.`, `+` → `\+`) entre guillemets ; la grammaire n'admet dans le motif que `[A-Za-z0-9 _/-]`, `\.` et `\+`. Une condition d'UA équivaut donc à « contient, sans casse ». Des deux côtés, chaque condition est confrontée à un **corpus d'UA protégés** (`tests/fixtures/htaccess/protected-uas.txt` : moteurs, aperçus sociaux, navigateurs courants, AiUser) ; un seul UA du corpus touché fait refuser le bloc | Un `.` non échappé élargit la règle ; on ne bloque jamais un moteur ni un navigateur par accident de motif |
| **Toute règle expire dans Apache lui-même** : chaque groupe porte sa `RewriteCond %{TIME} <…` ; IP 24 h par défaut, bornée à (now, now + 25 h] ; UA 30 jours par défaut, bornée à (now, now + 31 j]. `%{TIME}` est l'heure locale du serveur web : le veilleur l'écrit dans le fuseau du site (`[sites.logs] tz`, #1 ; sans fuseau, pas de proposition d'IP ni d'UA) et l'agent vérifie la borne avec sa propre heure locale (refus si hors borne : un écart de fuseau se voit, il n'élargit rien). L'IP vient de `Entry.ip`, jamais d'un en-tête ; elle s'écrit sous forme canonique (IPv4 décimale ; IPv6 compressée en minuscules, `inet_pton`/`inet_ntop` côté agent) et échappée (`^…$`, points et deux-points) | TTL exigé pour toutes les règles, sans écriture au moment de l'expiration ; une règle oubliée ne bloque pas indéfiniment |
| Paramètres de `htaccess-apply` : `{block, previous_sha256, new_sha256}` ; l'agent refuse si le `.htaccess` actuel n'a plus l'empreinte `previous_sha256` (`site recommend` la lit dans le dernier rapport, fichier critique `.htaccess`) ou si le contenu qu'il calcule n'a pas `new_sha256`. Le veilleur enregistre `new_sha256` comme référence attendue à la réussite de la commande : l'intégrité (`agent:integrity/modified:.htaccess`) ne s'ouvre pas pour un changement que Vigie a lui-même appliqué | Pas d'écriture sur un fichier modifié entre la proposition et l'application ; pas de fausse alerte d'intégrité |
| Application par l'agent, sous le verrou de son état : (1) validation du bloc ; (2) nouveau contenu = contenu actuel dont le bloc `vigie` est remplacé, ou ajouté en tête ; le bloc `# BEGIN sc_alwaysdata protection` du module PrestaShop, s'il existe, reste intact et au-dessous ; (3) **bac à sable** : un dossier aléatoire `vigie-essai-<hex>` (sans point initial, souvent interdit par le `.htaccess` du site) sous la racine, avec le nouveau `.htaccess` et une page témoin, interrogé sur l'URL du site avec un paramètre anti-cache : 200 attendu pour un UA de navigateur et pour Googlebot, 403 pour un UA visé par le bloc (s'il y en a) ; sinon refus ; dossier supprimé dans tous les cas ; (4) copie `.htaccess.vigie-prev` (mode de l'original), état `htaccess_pending {new_sha256}` écrit, puis **compare-and-swap** : relecture du `.htaccess`, refus s'il n'a plus `previous_sha256`, écriture par fichier temporaire (mode de l'original) et `rename` ; (5) **smoke-test** de l'accueil, anti-cache, UA de navigateur et Googlebot : même statut qu'avant la bascule, sinon retour à `.vigie-prev` **seulement si** le `.htaccess` a encore `new_sha256` (sinon `failed` « modifié pendant l'application », rien n'est écrasé) ; (6) `htaccess_pending` effacé. Un passage qui trouve un `htaccess_pending` (application interrompue) refait le smoke-test, et le retour arrière s'il échoue, avant toute autre chose | Garde-fous de l'issue : dry-run, `.prev`, rollback automatique ; jamais d'écrasement d'une modification d'un tiers ; un crash entre la bascule et le smoke-test ne laisse pas un site cassé sans contrôle |
| `htaccess-rollback` remet `.vigie-prev` (compare-and-swap sur l'empreinte attendue, puis smoke-test) ; une seule copie précédente, celle d'avant la dernière application | Retour arrière en une commande |
| Vecteurs partagés et **fuzz différentiel** : le générateur Rust (graine fixe) produit des blocs et des lignes mutées avec leur verdict dans `tests/fixtures/htaccess/vectors.json` ; le test PHP rejoue chaque vecteur et doit rendre le même verdict | Deux validateurs écrits deux fois divergent sinon en silence |
| L'écriture passe par le canal de commandes de l'agent, pas par FTP : l'issue demandait un accès « demandé au moment d'agir, jamais stocké » ; le canal n'en stocke aucun (décision du 2026-10-16) | Le canal de #10 remplace le besoin d'un accès FTP |
| `htaccess-apply` et `htaccess-rollback` deviennent disponibles (`CommandKind::available`) dans le même changement que la validation côté agent | Jamais l'un sans l'autre |

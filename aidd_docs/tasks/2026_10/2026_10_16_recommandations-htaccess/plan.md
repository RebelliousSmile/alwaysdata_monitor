## Decisions

| Decision | Why |
| -------- | --- |
| Séparer l'**analyse** (déterministe : `Analysis` de #8 → `Vec<Proposal>`, testée par cas) de la **génération** de texte (`Proposal` → bloc `.htaccess`), testée par fichiers de référence (golden files) | Exigence de l'issue ; le texte est la partie fragile |
| Gradation : un robot qui respecte robots.txt (`honours_robots`) → proposition robots.txt seulement ; un robot qui ne le respecte pas, de classe non protégée → règle d'UA ; une IP → règle d'IP seulement si son score propre est élevé, que son reverse DNS, résolu au moment de proposer, la classe hébergeur, et jamais pour une IP d'une classe protégée ni d'un site `behind_proxy` ; jamais rien contre `SearchEngine`, `OtherEngine`, `SocialPreview`, `Browser`, `AiUser`, ni un jeton robots-only (Google-Extended) en règle d'UA | Garde-fous de l'issue et protections décidées dans #8 |
| Une règle d'IP porte son expiration dans Apache lui-même : `RewriteCond %{TIME} <AAAAMMJJhhmmss` (24 h par défaut), l'IP vient de `Entry.ip` (champ client), jamais d'un en-tête | TTL exigé sans écriture automatique au moment de l'expiration ; jamais d'IP tirée de `X-Forwarded-For` |
| robots.txt reste une **proposition à appliquer à la main** (texte affiché par la CLI) : la liste fermée des commandes ne s'étend pas à robots.txt dans cette issue | Plus petite surface ; robots.txt n'exécute rien |
| Le bloc est délimité par deux lignes exactes `# BEGIN vigie` et `# END vigie` (au plus une paire dans le fichier, localisée par opérations de chaînes, jamais par regex) et sa **grammaire se valide par groupes**, par le veilleur à la génération **et par l'agent** avant toute écriture : `RewriteEngine On` une fois en tête, puis des groupes ; un groupe = des `RewriteCond` d'une seule sorte (UA : chaque ligne `[NC,OR]` sauf la dernière `[NC]` ; ou IP : une seule ligne), puis **exactement une** `RewriteCond %{TIME} <AAAAMMJJhhmmss`, puis exactement une `RewriteRule ^ - [F,L]`. Lignes de commentaire `# ` en ASCII imprimable `[ -~]`, sans `\`, sans `BEGIN`/`END`, en colonne 0. Fins de ligne LF seules ; aucun CR, tabulation, NUL ni ligne finissant par `\` (continuation Apache) ; 200 lignes et 16 Kio au plus. Toute autre ligne (`php_value`, `php_flag`, `AddHandler`, `SetHandler`, `AddType`, `Action`, `Include`, `auto_prepend_file`, `allow_url_include`, `Options`, `<Files>`…) fait refuser le bloc entier | Un `.htaccess` libre donne l'exécution de code ; la validation doit tenir même si le veilleur est compromis ; une condition `[OR]` mal chaînée ou une continuation de ligne changerait le sens du bloc |
| **Littéral d'UA = expression régulière** pour Apache : le littéral source n'admet que `[A-Za-z0-9][A-Za-z0-9 _/.+-]{2,63}` (premier caractère alphanumérique : un motif commençant par `-` serait lu comme un opérateur de `RewriteCond`) et s'écrit échappé (`.` → `\.`, `+` → `\+`) entre guillemets ; la grammaire n'admet dans le motif que `[A-Za-z0-9 _/-]`, `\.` et `\+`. Une condition d'UA équivaut donc à « contient, sans casse ». Des deux côtés, chaque condition est confrontée à un **corpus d'UA protégés** (moteurs, aperçus sociaux, navigateurs courants, AiUser, UA de Vigie, webhooks de paiement, bouclages de CMS `WordPress/` et PrestaShop) : constante de `vigie-agent.php` (fichier unique déployé), égale à `tests/fixtures/htaccess/protected-uas.txt` par un test ; un seul UA du corpus touché fait refuser le bloc | Un `.` non échappé élargit la règle ; on ne bloque jamais un moteur ni un navigateur par accident de motif |
| **Toute règle expire dans Apache lui-même** : chaque groupe porte sa `RewriteCond %{TIME} <…` ; IP 24 h par défaut, bornée à (now, now + 25 h] ; UA 30 jours par défaut, bornée à (now, now + 31 j]. `%{TIME}` est l'heure locale du serveur web : le veilleur l'écrit dans le fuseau du site (`[sites.logs] tz`, #1 ; sans fuseau, pas de proposition d'IP ni d'UA) et l'agent vérifie la borne dans le fuseau explicite de sa configuration (`config.json` : `tz`, appliqué par `date_default_timezone_set`, jamais celui de php.ini) ; **le bac à sable sonde l'horloge réelle d'Apache** par deux groupes témoins à UA aléatoire (`vigie-probe-<hex>a`, `%{TIME} <` now + 30 min → 403 attendu ; `vigie-probe-<hex>b`, `%{TIME} <` now − 30 min → 200 attendu) ; un écart → refus « horloge Apache ≠ horloge agent ». Heure d'hiver : une heure répétée peut porter une règle de 24 h à 25 h, dans la borne (documenté). L'IP vient de `Entry.ip`, jamais d'un en-tête ; elle s'écrit sous forme canonique (IPv4 décimale ; IPv6 compressée en minuscules, `inet_pton`/`inet_ntop` côté agent) et échappée (`^…$`, points et deux-points) | TTL exigé pour toutes les règles, sans écriture au moment de l'expiration ; une règle oubliée ne bloque pas indéfiniment |
| Paramètres de `htaccess-apply` : `{block, previous_sha256, new_sha256}` ; l'agent refuse si le `.htaccess` actuel n'a plus l'empreinte `previous_sha256` (`site recommend` la lit dans le dernier rapport, fichier critique `.htaccess`) ou si le contenu qu'il calcule n'a pas `new_sha256`. La référence d'intégrité suit la décision « Intégrité » ci-dessous | Pas d'écriture sur un fichier modifié entre la proposition et l'application ; pas de fausse alerte d'intégrité |
| Application par l'agent, sous le verrou de son état : (1) validation du bloc ; (2) nouveau contenu = contenu actuel dont le bloc `vigie` est remplacé, ou ajouté en tête ; le bloc `# BEGIN sc_alwaysdata protection` du module PrestaShop, s'il existe, reste intact, au-dessus ou au-dessous ; (3) **bac à sable différentiel** (décision dédiée : dossiers `-a`/`-b`, nonces, sondes d'horloge dans `-b` seulement, dont le `.htaccess` diffère donc de `new_sha256`) ; refus si un contrôle échoue ; dossiers supprimés dans tous les cas ; (4) **compare-and-swap** : relecture du `.htaccess`, refus s'il n'a plus `previous_sha256` ; puis copie précédente écrite **dans le dossier privé de l'agent** (0700, `htaccess.prev`, fichier temporaire + `rename` ; la copie de la bascule précédente gardée en `htaccess.prev.old` jusqu'à la réussite du `rename` du `.htaccess`) depuis les octets en mémoire vérifiés égaux à `previous_sha256`, état `htaccess_pending {command_id, prev_sha256, new_sha256, statuts_avant}` écrit, puis écriture du `.htaccess` par fichier temporaire (mode de l'original) et `rename` (fenêtre résiduelle entre relecture et `rename` acceptée, documentée) ; (5) **smoke-test** de l'accueil, anti-cache, UA de navigateur et Googlebot : même statut qu'avant la bascule, sinon retour à la copie privée **seulement si** le `.htaccess` a encore `new_sha256` (sinon `failed` « modifié pendant l'application », rien n'est écrasé) ; (6) `htaccess_pending` effacé. Un passage qui trouve un `htaccess_pending` (application interrompue), en tête du rappel de `with_state` et avant le traitement de `running`, décide d'après l'empreinte actuelle du `.htaccess` : `new_sha256` → smoke-test contre `statuts_avant`, puis `ok` ou retour arrière et `failed` ; `prev_sha256` → `failed` « bascule non faite », rien d'écrit ; autre → `failed` « modifié pendant l'application », rien d'écrit ; toujours avec `current_sha256`. `load_state` migre un `state.json` de 0.2.0 en ajoutant `htaccess_pending: null` (jamais « état illisible » pour un agent déjà en place). Requêtes de l'agent : `url` en https, aucune redirection suivie, 5 s par requête et 30 s en tout, pris sur le passage | Garde-fous de l'issue : dry-run, `.prev`, rollback automatique ; jamais d'écrasement d'une modification d'un tiers ; un crash entre la bascule et le smoke-test ne laisse pas un site cassé sans contrôle |
| `htaccess-rollback {expected_current_sha256, prev_sha256}` remet la copie privée de l'agent, refusé si elle n'a pas `prev_sha256` ou si le `.htaccess` n'a pas `expected_current_sha256` (compare-and-swap), puis smoke-test ; une seule copie précédente. Un `.htaccess` absent à l'application : création, et retour arrière par suppression | Retour arrière en une commande ; une copie dans le webroot pourrait être réécrite par une porte dérobée puis restaurée sans revalidation |
| **Bac à sable différentiel** : deux dossiers `vigie-essai-<hex>-a` (ancien contenu) et `-b` (nouveau), chacun avec une page témoin portant un nonce aléatoire ; aucune redirection suivie. Pour un UA de navigateur, Googlebot et un échantillon du corpus : même statut dans les deux dossiers ; pour **chaque** groupe d'UA : pas 403 dans `-a`, 403 dans `-b` ; plus les deux sondes d'horloge. Un 200 sans le nonce → refus « bac à sable non représentatif ». Le bac à sable vérifie la syntaxe et le bloc ; l'effet à la racine relève du smoke-test (documenté) | Un `.htaccess` enfant avec `RewriteEngine On` n'hérite pas des réécritures du parent : comparer à un 200 absolu échouerait (redirection https, `index.php`) ou validerait l'ancien fichier |
| **Ce que Vigie ne bloque jamais** : IP protégées (IP sortante du veilleur, adresse source des retraits signés de l'agent relevée par le veilleur — `X-Forwarded-For` lu seulement du proxy local de confiance —, `[sites.logs] protect_ips`) ; `/vigie-essai-*` et l'UA de Vigie exclus de l'analyse ; le littéral d'une règle d'UA est **le jeton du catalogue** du robot, jamais une sous-chaîne lue dans un log, et la classe `Unknown` n'a pas de règle d'UA ; jetons génériques (`curl`, `python-requests`, `Java`, `Go-http-client`, `wget`…) refusés comme littéral | Le veilleur lui-même (UA d'outil, IP d'hébergeur, sans statiques) atteindrait le niveau élevé du score ; webhooks de paiement et tâches planifiées ne doivent pas tomber |
| **Intégrité** : tout résultat `htaccess-*` porte `data.current_sha256` ; tant qu'une commande `htaccess-*` est `served` ou `unknown`, `compare()` admet pour `.htaccess` ses empreintes attendues (`new_sha256`, et `prev_sha256` pour un retour arrière) sans ouvrir `modified:.htaccess` ; la référence suit `current_sha256` seulement s'il fait partie de ces empreintes | Le rapport part avant le retrait : sans cela, le rapport portant `new_sha256` ouvrirait l'incident avant le résultat `ok` ; la reprise et les retours arrière restent couverts |
| **Bloc cumulatif** : le rapport ne porte que des empreintes, donc le bloc en place est celui du dernier `htaccess-apply` `done` dont `current_sha256` égale l'empreinte `.htaccess` du dernier rapport ; un nouvel `htaccess-apply` en reprend les groupes encore valides, retire les expirés, et `site recommend` affiche le diff. Sans cette correspondance (fichier modifié hors de Vigie, retour arrière, première application), `--apply` exige `--replace` et le diff porte « règles en place inconnues » ; le bloc `sc_alwaysdata` du module peut être au-dessus ou au-dessous du bloc `vigie` (les deux ordres admis ; test : `HtaccessDoctor::removeUaRules` laisse le bloc `vigie` intact). L'IP est comparée à `%{REMOTE_ADDR}` : une IPv4 mappée `::ffff:` ou l'IP d'un proxy rend la règle inerte (documenté) | Une application ne retire pas en silence des règles actives ; coexistence avec le module |
| Vecteurs partagés et **fuzz différentiel** : le générateur Rust (graine fixe) produit des blocs et des lignes mutées avec leur verdict dans `tests/fixtures/htaccess/vectors.json` ; le test PHP rejoue chaque vecteur et doit rendre le même verdict | Deux validateurs écrits deux fois divergent sinon en silence |
| L'écriture passe par le canal de commandes de l'agent, pas par FTP : l'issue demandait un accès « demandé au moment d'agir, jamais stocké » ; le canal n'en stocke aucun (décision du 2026-10-16) | Le canal de #10 remplace le besoin d'un accès FTP |
| `htaccess-apply` et `htaccess-rollback` deviennent disponibles (`CommandKind::available`) dans le même changement que la validation côté agent | Jamais l'un sans l'autre |

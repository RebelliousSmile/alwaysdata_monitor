# Plan: Inventaire CycloneDX/purl relevé par l'agent PHP (F5)

## Overview

| Field      | Value |
| ---------- | ----- |
| **Goal**   | Donner au veilleur, pour chaque site doté de l'agent PHP, la liste de ses composants (purl + version brute) dans un format standard, sans que le site connaisse une base de failles, pour que F7 (#21) les rapproche en local |
| **Source** | Issue GitHub #19 ; décisions F0 dans `vigie/docs/decisions.md` (« Failles connues ») et conventions purl de `vigie/docs/failles.md` (#14) ; modèle de transport `/r/v1/logs` (#1 : `logs/receive.rs`, `serve.rs`, `command/key.rs`) ; état de l'agent et migration de `state.json` (#13) ; registre de capacités (#4, `capability.rs`) |
| **Dépendances** | #14 (F0) fait. Bloque F6 (#20, même contrat) et F7 (#21, rapprochement). **F1 (#15) prend la migration 0015 en parallèle** : F5 prévoit **0016**, à renuméroter au prochain numéro libre au moment de la fusion. Si F1 a déjà fusionné un module purl côté Rust, F5 le réutilise au lieu d'en créer un |

### Ce qui existe et sert de modèle

- **Transport signé à préfixe de domaine** : `/r/v1/logs` (`vigie-logs-v1\n`, `seq` propre dans `site_keys.last_logs_seq`, 404 muet, `deny_unknown_fields`, horloge ±300 s, écriture par le writer de `serve` en transaction IMMEDIATE). F5 reprend exactement ce parcours avec `vigie-inventory-v1\n` et `site_keys.last_inventory_seq`.
- **État de l'agent** : `state.json` (0600, écriture atomique, `with_state` sous `flock` `LOCK_NB` de `state.lock`), migré sans perte de 0.2/0.3 vers 0.4 par ajout de `htaccess_pending` (`STATE_KEYS_0_3`). F5 ajoute la clé `inventory` et migre 0.2–0.4.
- **Lecture sans suivre de lien hors racine** : `locate()`, `locate_dir()`, `inside()` ; lecture texte bornée de `$wp_version` (`wordpress_version()`), jamais d'`include`.
- **Repli de clé en rotation** : `pending_new_secret()` (comme `send_report` et `send_log_batch`).
- **Fixture signée et interopérabilité** : `make-interop-fixture.php` → `tests/fixtures/php-signed-report.json` → `tests/interop.rs` ; vecteurs partagés PHP/Rust (`commands-vectors.json`).
- **Bout en bout** : `tests/agent_e2e.rs`, PHP 8.1 épinglé par digest dans `vigie.yml`.

## Decisions

| Decision | Why |
| -------- | --- |
| **Transport** : `POST /r/v1/inventory`, corps signé par la clé de rapport sur `vigie-inventory-v1\n` + octets bruts (`DOMAIN_INVENTORY` dans `command/key.rs`, `const DOMAIN_INVENTORY` dans l'agent). Vérifications dans l'ordre de `/r/v1/logs` : taille et délai, site connu avec `[sites.inventory] source` déclarée (runtime effectif `php` exigé au chargement), clé enregistrée, signature, schéma, horloge ±300 s, puis sous verrou d'écriture `seq` strictement croissant (`site_keys.last_inventory_seq`, propre à l'inventaire) et débit. 404 sans corps sur tout refus, raison au journal avec `request_id`. Point d'entrée dérivé de `endpoint` (qui doit finir par `/r/v1/report`, comme pour les logs) | Une signature ne vaut que pour son point d'entrée : un rapport, un retrait ou un lot de logs rejoués sur `/r/v1/inventory` échouent à la signature, et inversement. Même modèle que #1, déjà audité |
| **Enveloppe Vigie + document CycloneDX** : `{"v":1,"type":"inventory","site","seq","sent_at","agent","complete","skipped","bom":{…}}`, `deny_unknown_fields` sur l'enveloppe **et** sur chaque objet du sous-ensemble CycloneDX. `complete` (booléen) est faux dès qu'une borne a tronqué le relevé (composants, temps, taille, fichier de verrouillage trop gros ou illisible) ; `skipped` compte les composants ou sources écartés (0 à 100 000) | Le BOM reste un CycloneDX pur, réutilisable par F6 ; ce qui est propre à Vigie (séquence, complétude) reste hors du BOM. F7 ne doit jamais conclure « faille corrigée » d'un composant absent d'un inventaire incomplet |
| **Sous-ensemble CycloneDX** : `bomFormat` = `CycloneDX`, `specVersion` ∈ {`1.6`, `1.7`} (l'agent émet `1.7`, décision F0), `serialNumber` = `urn:uuid:<UUID v4>`, `metadata.timestamp` (RFC 3339 UTC, à la seconde), `metadata.component` = `{"type":"application","name":"<site>"}` (identifiant Vigie seul, égal à `site`), `components[]` = `{type, name, version, purl, scope, properties}`. **Liste blanche** (F0 révisée) : l'agent n'émet que ces champs ; le veilleur refuse tout le document (404, schéma) s'il porte `authors`, `supplier`, `licenses` ou tout autre champ, ou une propriété dont le nom n'est pas l'une des propriétés `vigie:*` listées. `type` ∈ {`application` (noyaux WordPress et PrestaShop), `library` (le reste)}. `properties` : liste fermée `vigie:path` (obligatoire), `vigie:scope` (obligatoire), `vigie:parent` (thème enfant seulement). Ni licences, ni hachages, ni graphe `dependencies`, ni `bom-ref` en V1 (limite écrite dans `protocole-agent.md`) | Taille et utilité : le rapprochement n'a besoin que du purl et de la version. Un sous-ensemble fermé se valide entièrement et ne laisse passer aucun champ libre vers la base |
| **`scope` CycloneDX ≠ scope Vigie** : CycloneDX 1.7 n'admet que `required`, `optional`, `excluded`. Le champ `scope` vaut `required` pour tout composant d'exécution (noyau, extensions, mu-plugins, thèmes, modules, `packages` Composer, paquets npm hors `dev`) et `excluded` pour les dépendances de développement ; le scope Vigie de l'issue (`required` / `dev` / `mu`) part dans la propriété `vigie:scope`. **Écart assumé à la lettre de l'issue**, qui mettait `dev`/`mu` dans `scope` | Un `scope: "dev"` rendrait le document invalide pour tout outil CycloneDX ; `excluded` est la valeur de la spec pour « usage hors exécution » |
| **purl** (F0 révisée après relecture, à reporter dans `failles.md` si ce n'est pas déjà fait) : `pkg:wordpress/core/core@v` (proposition purl-spec n° 347), `pkg:wordpress/plugin/<slug>@v`, `pkg:wordpress/theme/<slug>@v`, `pkg:prestashop/core/prestashop@v`, `pkg:prestashop/module/<nom>@v`, `pkg:composer/<vendor>/<nom>@v`, `pkg:npm/<nom>@v` ou `pkg:npm/%40<scope>/<nom>@v`. **Seul Composer est mis en minuscules** (vendor et nom) ; npm (et cargo, pour F6) est sensible à la casse et n'est jamais modifié ; slugs WordPress et noms techniques PrestaShop sont pris tels quels (nom du dossier) ; le chemin réel est dans `vigie:path`. Segments et version encodés en pourcentage hors `[A-Za-z0-9._~-]` (le `+` d'une version devient `%2B`). Version vide → purl sans `@`. `name` du composant = nom du purl décodé (`vendor/nom` pour Composer, `@scope/nom` pour npm). **Le veilleur recalcule le purl canonique** à partir du type, du nom et de la version et écarte (compte) tout composant dont le purl diffère | Un identifiant commun aux deux côtés ; le veilleur ne fait pas confiance à l'encodage de l'agent, et la même fonction servira F6 et F7 |
| **Types admis selon le CMS du site** (registre #4, `match` sans joker) : `wordpress` pour un site `kind = wordpress`, `prestashop` pour `kind = prestashop`, `composer` et `npm` pour tout site au runtime `php`. Un composant d'un type non admis est **écarté et compté** (`dropped`), l'inventaire restant accepté ; un purl d'un type inconnu aussi. `cargo` n'est pas admis en V1 (aucun site PHP n'en a ; F6 décidera) | Fail-closed sans casser un agent dont le `kind` local diffère de `config.toml` ; le CMS d'un site vient de la configuration du veilleur, jamais de l'agent |
| **Ce que l'agent relève selon son `kind`** : `kind` accepte désormais `prestashop` (en plus de `wordpress` et `generic`, aligné sur `SiteKind`) ; `wordpress` → cœur, extensions, mu-plugins, thèmes ; `prestashop` → noyau, modules ; tous → `composer.lock` et `package-lock.json`. Aucune détection automatique du CMS | Rien de deviné ; un site générique ne se voit jamais attribuer un cœur WordPress parce qu'un dossier `wp-includes` traîne |
| **Paquets Composer qui sont des composants de CMS** (F0 révisée) : sur un site `prestashop`, un paquet `composer.lock` de `type` `prestashop-module` n'est **pas** émis en `pkg:composer` : le module `<x>` (`extra.installer-name`, sinon la partie après `/`) est émis en `pkg:prestashop/module/<x>` avec la version lue dans `modules/<x>/config.xml` (repli `$this->version`), c'est-à-dire par le relevé des modules ; absent de `modules/`, il n'est pas émis (non installé). Sur un site `wordpress`, `wpackagist-plugin/<slug>` et `wpackagist-theme/<slug>` (Bedrock) deviennent `pkg:wordpress/plugin/<slug>` et `pkg:wordpress/theme/<slug>`, version du lockfile, `vigie:path` = le lockfile. **Un seul composant par purl sans version** : le relevé sur disque l'emporte sur le lockfile | Le `composer.lock` de PrestaShop 8 garde la version d'installation des modules natifs, périmée après une mise à jour depuis le back-office : seule la version sur disque est vraie. Bedrock installe les extensions par Composer : sans correspondance, elles échapperaient au rapprochement WordPress |
| **Lecture seule et sans exécution** : uniquement `file_get_contents` borné, `json_decode` et `simplexml_load_string` ; jamais `include`, `require`, `eval`, `token_get_all`, `highlight_file`, ni appel shell. Expressions régulières bornées (ancrées, quantificateurs bornés) sur les 8 premiers Kio d'un en-tête ; la valeur entière, coupée de ses espaces, doit correspondre à `^[0-9A-Za-z.+_~-]{1,64}$`, sinon **version vide** (jamais tronquée ni devinée : `1.0'; system(…)` → `""`) | Exigence de l'issue ; un en-tête hostile ne peut ni s'exécuter ni injecter une version |
| **XML des modules PrestaShop** : `config.xml` lu sur 8 Kio ; refusé d'emblée s'il contient `<!DOCTYPE` ou `<!ENTITY` (insensible à la casse) ; sinon `simplexml_load_string($xml, \SimpleXMLElement::class, LIBXML_NONET \| LIBXML_NOCDATA)`, **sans** `LIBXML_NOENT` ni `LIBXML_DTDLOAD`, erreurs libxml internes. Sans `config.xml` exploitable (absent, refusé, extension simplexml absente), repli sur `$this->version = '…'` dans les 32 premiers Kio de `modules/<nom>/<nom>.php` | Pas d'entité externe ni d'expansion (« billion laughs ») ; le constructeur d'un module PrestaShop est plus loin que l'en-tête d'une extension WordPress |
| **Bornes** : 2 000 composants ; 8 Kio par en-tête (`.php` de premier niveau d'une extension, `style.css`, `config.xml`), 32 Kio pour le fichier principal d'un module, 20 fichiers `.php` examinés par dossier d'extension (le `<slug>.php` d'abord) ; 500 entrées par dossier listé (`plugins`, `mu-plugins`, `themes`, `modules`) ; `composer.lock` et `package-lock.json` de 4 Mio au plus, `json_decode` en profondeur 32 ; 10 chemins supplémentaires de chaque sorte ; **20 s** de relevé (`hrtime`), au-delà `complete = false`. Profondeur : premier niveau des dossiers d'extensions seulement ; liens symboliques suivis seulement si la cible reste dans `root` (`locate`/`locate_dir`). Chemin relatif assaini : segments `[A-Za-z0-9._@+~-]`, 200 caractères au plus, sinon composant écarté et compté | Mémoire et temps bornés sur un hébergement mutualisé ; même règle de liens que l'intégrité |
| **Corps plafonné à 512 Kio, sans gzip** : l'agent retire les derniers composants (dans l'ordre de relevé : cœur, extensions, mu, thèmes, noyau PS, modules, Composer, npm) tant que le corps dépasse 524 288 octets, et met `complete = false`. Le veilleur lit au plus 512 Kio en 10 s (`read_agent_body` paramétré par la limite), le reste 404 | Ordre de grandeur : ~250 octets par composant, un site WordPress courant tient en 10 à 30 Kio. Pas de `Content-Encoding` : pas de bombe de décompression à borner, et la signature porte sur les octets reçus sans transformation |
| **Envoi quand l'inventaire change, et au moins toutes les 24 h** : l'agent relève à chaque passage (borné), calcule l'**empreinte** SHA-256 de la liste canonique (composants triés par `purl` puis `vigie:path`, sans `serialNumber` ni `timestamp`) et l'envoie si elle diffère de celle du dernier 204, ou si le dernier 204 date de plus de 24 h. Après un refus ou un échec réseau, pas de nouvel essai avant 1 h | Une mise à jour d'extension est vue en 5 min ; un veilleur pas encore à jour ou un site sans runtime `php` ne reçoit pas un 404 toutes les 5 min |
| **État de l'agent dans `state.json`**, clé `inventory` : `null` ou `{"seq", "sha256", "sent_at", "failed_at"}` (entiers, `sha256` vide ou 64 hex). Lecture et écriture sous `with_state` ; le relevé se fait **avant** de prendre le verrou, l'envoi sous verrou (comme les commandes). `seq` = `max(seq + 1, heure en ms)`, écrit avant l'envoi. Migration : un état à 5 clés (0.2/0.3) reçoit `htaccess_pending: null` et `inventory: null`, un état à 6 clés (0.4) reçoit `inventory: null` ; réécrit au format 0.5.0 au prochain `save_state`. Un `inventory` forgé fait refuser l'état (« État illisible ») | Demande de l'issue (empreinte dans `state.json`, migration comme #13) ; un relevé lent ne bloque pas le canal de commandes d'un passage concurrent |
| **Activation explicite connue du veilleur** (F0 révisée : `vulns` est surveillé dès qu'une source d'inventaire est déclarée) : nouvelle section `[sites.inventory]` de `config.toml`, `source = "agent-php"` (enum fermée, F6 ajoutera la sienne), admise seulement pour un runtime effectif `php` (refus au chargement de la configuration sinon). Sans elle, `/r/v1/inventory` refuse le site (404, raison `InventoryClosed`). Le registre expose `capability::inventory_source(site)`, que F7 utilisera comme condition d'existence (`Needs::InventorySource`) du contrôle `vulns` ; F5 n'ajoute pas le contrôle. À noter pour F7 : source déclarée sans inventaire reçu depuis 25 h → constat « inventaire absent » | L'état « surveillé » doit se lire dans la configuration du veilleur, jamais se déduire de ce qu'un agent envoie ou non ; fail-closed comme `[sites.logs] source` |
| **Configuration de l'agent** : section facultative `inventory` de `config.json` : `{"enabled": true, "composer": [...], "npm": [...]}` ; `enabled` obligatoire (booléen), `composer` et `npm` facultatives, 10 chemins relatifs au plus (`relative_path`), en plus de `composer.lock` et `package-lock.json` à la racine, lus s'ils existent. **Section absente = inventaire désactivé** | Un agent 0.5.0 posé sur une configuration 0.4 ne change pas de comportement ; activer est un geste explicite, comme `commands` et `logs` |
| **Stockage côté veilleur** (migration **0016**, prochain numéro libre) : `site_keys.last_inventory_seq` ; `site_inventory` (id `AUTOINCREMENT`, site, `digest` SHA-256 recalculé par le veilleur sur la liste canonique, `spec_version`, `serial`, `generated_at`, `agent`, `complete`, `skipped`, `dropped`, `components`, `received_at` = première réception de ce contenu, `seen_at` = dernière) ; `site_inventory_components` (inventaire, `ecosystem`, `purl` sans version, `purl` complet, `name`, `version`, `scope` Vigie, `type`, `path`, `parent`), clé `(inventory, purl, path)`, index sur le purl sans version pour F7. Le corps brut n'est jamais stocké | F7 interroge les composants par purl ; un document brut ferait doublon et garderait des champs non validés |
| **Renvoi inchangé non réécrit** : même `digest` que le dernier inventaire du site → seuls `seen_at` et `last_inventory_seq` avancent, aucune ligne nouvelle ; sinon nouvel inventaire et ses composants dans une même transaction IMMEDIATE. Débit : un inventaire accepté (nouveau ou inchangé) par site et par 240 s au plus | L'envoi des 24 h ne gonfle pas l'historique ; un agent fou ne remplit pas la base |
| **Conservation** : le dernier inventaire d'un site est gardé tant que le site a une clé ; les précédents dont `seen_at` a plus de 30 jours sont purgés par `tick` (avec `purge_logs`). `site remove` purge tout l'inventaire du site ; `site rotate-key` remet `last_inventory_seq` à zéro et garde l'inventaire | Décision F0 (dernier + 30 jours, purgé avec le site) ; une rotation de clé ne change pas ce que contient le site |
| **Pas une preuve de vie** : un inventaire accepté ne touche ni `reports.last_valid_at`, ni les incidents, ni le silence ; il n'ouvre aucun constat en F5. Aucun contrôle n'est ajouté au registre (`vulns` viendra avec F7) ; seuls `capability::inventory_source(site)` et `capability::inventory_ecosystems(kind)` y sont déclarés | Le battement de cœur reste porté par le rapport ; F5 ne fait que relever |
| **Agent 0.5.0** : `VERSION = '0.5.0'` ; nouveau mode `--inventory` qui affiche l'enveloppe non signée sans rien envoyer (exclusif avec `--dry-run` et `--init`) ; ordre d'un passage : rapport, commandes, **inventaire**, logs ; un échec d'inventaire donne le code 1 (2 pour une erreur de configuration ou d'état) sans empêcher les logs | Vérification à la pose sans toucher au veilleur ; les logs, plus longs, restent en dernier |
| **Vecteurs et interopérabilité** : `make-interop-fixture.php` régénère `php-signed-report.json` (agent 0.5.0) et écrit `php-signed-inventory.json` (inventaire du site fictif WordPress de la phase 2, graine fixe) et `inventory-vectors.json` (domaine, corps signés valide, rapport rejoué, lot de logs rejoué, inventaire signé sans préfixe). `AgentTest.php` vérifie que les fichiers suivis correspondent à ce que l'agent produit ; `interop.rs` et `commands_vectors.rs` (ou un `inventory_vectors.rs`) les rejouent | Même garantie que pour les rapports : le Rust vérifie ce que sodium a signé, octet pour octet |
| **Fixtures fictives** (`.claude/rules/07-quality/7-public-repo-data.md`) : sites « site A » (WordPress) et « site B » (PrestaShop 1.6 et 8), slugs inventés (`exemple-formulaire`, `exemple-cache`…), vendors Composer `exemple/…`, domaines `example.org`. Les fichiers hostiles qui ressemblent à du code dangereux (`system(`), les liens symboliques et les en-têtes géants sont **créés par le test dans un dossier temporaire**, jamais versionnés | Dépôt public ; l'antivirus Windows met en quarantaine ce qui ressemble à un webshell (`agent-php.md`) ; un lien symbolique versionné casse sous Windows |
| Hors périmètre V1, écrit comme limite : disposition Bedrock complète (`composer.lock` hors de `web/`, extensions sous `web/app/plugins` : V1 ne lit que des chemins sous `root`), `roots/wordpress` et `johnpbloch/wordpress` comme cœur, `vendor/composer/installed.json` sans `composer.lock`, `package-lock.json` v1, `yarn.lock`/`pnpm-lock.yaml`, drop-ins WordPress (`object-cache.php`…), thèmes PrestaShop, licences et hachages, lecture de l'inventaire par l'API, la console ou la CLI (F7) | Bornes de l'issue ; chaque ajout se fera sans changer le contrat (nouvelles sources = nouveaux composants) |

## Decisions

| Decision | Why |
| -------- | --- |
| **Jeton sous Windows dans le Credential Manager** : `[target.'cfg(windows)'.dependencies]` `keyring-core = "1"` et `windows-native-keyring-store = { version = "1", default-features = false }` (jamais la façade `keyring`, qui se rabat en silence sur un stockage en mémoire sans sa feature native) ; store construit explicitement (pas de store global par défaut), persistance **`Local`** (jamais `Enterprise`, qui suit le profil itinérant), cible fixe `vigie-console/device`. Le CI Android vérifie `cargo tree --target aarch64-linux-android -i keyring-core` vide. Erreurs du trousseau traduites en messages fixes (jamais `{err}` : `BadEncoding` porte les octets du secret) | Exigence « keyring OS » tenue sous Windows, sans fuite vers d'autres postes ni stockage factice |
| **Migration et échecs** : lecture de `device.json` par une struct héritée (`token: Option<String>`, `#[serde(default)]`) ; si le fichier porte un jeton, il fait foi : écriture au trousseau, relecture et comparaison, puis réécriture atomique du fichier sans jeton (rejouable sans dommage). Échec → on continue avec le jeton du fichier, `Status.token_storage` (`keyring`, `file_legacy` pour l'échec de migration sous Windows, `private_file` sous Android) affiché dans Réglages, seul `file_legacy` en état dégradé, nouvel essai à chaque lancement : aucun appareil appairé n'est bloqué. Écriture refusée **pendant l'appairage** (stratégie de groupe) → révocation du jeton émis (`DELETE /api/v1/devices/self`) avant de rendre l'erreur. `forget`, `unpair` et 401 suppriment l'entrée du trousseau **et** le fichier, même si l'une échoue ; une entrée du trousseau est effacée au démarrage seulement si `device.json` est absent (`NotFound`), jamais s'il est illisible. Sous stratégie de groupe interdisant le trousseau, un appareil déjà appairé reste appairé (fichier) mais un nouvel appairage est refusé : asymétrie décidée et écrite. Un retour à la 0.1.1 ne lit pas le nouveau fichier : ré-appairer (documenté) | Pas de perte silencieuse du jeton ; pas de jeton orphelin valide |
| **Android** : le jeton reste dans le fichier du stockage privé de l'application (0600). Un store Keystore existe (`android-native-keyring-store`) mais est écarté par choix (crate jeune, JNI), écrit dans `decisions.md`. **Sauvegarde et transfert coupés** : le fichier du jeton vit dans le dossier `no_backup` de l'application (exclu de toute sauvegarde et de tout transfert ; chemin vérifié par un test) ; en plus, après `tauri android init`, `console.yml` et `console-release.yml` écrivent `res/xml/data_extraction_rules.xml` (`<cloud-backup>` et `<device-transfer>` excluant `root`, `file`, `database`, `sharedpref`), ajoutent `android:dataExtractionRules` et `android:allowBackup="false"` au manifeste, et vérifient l'APK produit (`aapt2 dump xmltree` : attribut et fichier présents). `fullBackupContent` est ignoré à partir d'Android 12, et `allowBackup` seul n'y coupe pas le transfert d'appareil à appareil | Sans cela la sauvegarde automatique et le transfert de téléphone copieraient le jeton : deux appareils indiscernables pour la révocation |
| Abstraction `SecretStore` (Windows, fichier privé Android, mémoire pour les tests, avec échecs provoqués : écriture refusée, relecture différente) ; le jeton ne passe jamais au webview (commandes Tauri qui rendent les données, jamais le jeton) ; test : aucun `ApiError` ne contient le jeton. Test Windows réel en `#[cfg(windows)]` (cible unique par exécution, nettoyage par `Drop`, persistance relue `Local`) dans `cargo test` du runner `windows-latest` | Testable sur Linux ; preuve réelle sous Windows |
| **Garde-fous verrouillés par des tests** : CSP sans `unsafe-*` ni origine externe (existant), pas de `withGlobalTauri` ni d'URL distante ; capacités limitées à `core:default` et, sur mobile, au scanner (test qui lit `capabilities/*.json`) ; `vue/no-v-html` en erreur (#5) et test qui refuse `v-html`, `innerHTML`, `outerHTML`, `insertAdjacentHTML` dans `src/` hors `*.spec.ts` ; aucun plugin `fs`, `shell`, `http` dans `Cargo.lock` ni `pnpm-lock.yaml` (transitifs compris) ; liste de `generate_handler!` figée par test et `ack` seule requête non-GET de `client.rs` hors `pair` et `unpair` | Exigences « CSP stricte », « capacités inutiles désactivées », « échappement », « la GUI propose » |
| **Écran Trafic** (maquette `Site.dc.html`) : onglet Visiteurs alimenté par `GET /api/v1/sites/{id}/logs/ips` ; robots vus et dépassements de règles (maquette Blocages) et charge par heure (maquette Ressources) par `GET /api/v1/sites/{id}/logs` ; onglet Journal reste « pas encore disponible » (aucune ligne brute n'est servie, par décision RGPD). Les actions d'écriture des maquettes (« Bloquer cette IP », « Bloquer l'abonnement (/64) », « Autoriser », « Appliquer ») deviennent des **propositions non exécutables** : texte de la commande `vigie site recommend <site>` à passer sur le VPS (garde-fous #10 et #13) ; #13 fusionné est un prérequis de la 0.2.0. Trois états : 404 → « pas encore disponible », `{"analysis": null}` → « analyse en attente », sinon données. `features.ts` : la constante `LOGS` est réécrite (le veilleur reçoit les logs poussés par l'agent) | Exigence « vue logs » ; la GUI propose, ne fait jamais d'application |
| **Contrat de l'API #5** : `409 cursor_expired` (code lu dans le corps) → reprise à la page 1, distinct de `conflict` ; `400 bad_request` et `415` → message fixe ; `429` → « trop de requêtes, réessayer dans N s » d'après `Retry-After`, sans relance automatique ; `next_cursor` en `#[serde(default)]`. Prérequis de publication de la 0.2.0 : #5 phase 2 et #8 phase 3 déployées sur le VPS | Pas de mauvais message, pas de vue cassée face à un VPS en retard |
| Listes paginées : incidents clos et verdicts d'IP par « Afficher plus » ; le cas « 120 incidents » tourne dans `tests/contract.rs` contre le vrai routeur du veilleur | Pagination de #5 |
| Aucune écriture nouvelle : l'acquittement reste la seule écriture | Exigence « la GUI propose, ne fait jamais d'application automatique » |
| Version 0.2.0 de la console ; release par le workflow existant (tags `console-v*`), publiée par l'exploitant | Releases déjà en place |

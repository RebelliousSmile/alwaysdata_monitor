# Plan: Failles, modèle OSV interne, stockage et comparateurs de versions (F1)

## Overview

| Field      | Value |
| ---------- | ----- |
| **Goal**   | Poser le socle de la série F côté veilleur : un format unique des failles quelle que soit la source, une base qui les garde, et un rapprochement « ce composant à cette version est-il touché ? » fiable par écosystème. Aucune source n'est branchée (F2, F3) : les tests utilisent des fixtures OSV publiques ou fictives |
| **Source** | Issue GitHub #15 ; décisions F0 (#14 : section « Failles connues » de `vigie/docs/decisions.md` et `vigie/docs/failles.md`, en cours d'écriture ; à défaut, les décisions reprises ci-dessous) ; recherche vérifiée du 2026-10-17 (exports OSV `schema_version: "1.9.0"`, spécification 1.9.2, écosystèmes `Packagist`, `npm`, `crates.io`, purl-spec #347 pour WordPress, aucun type purl PrestaShop) ; existant : `store.rs` (migrations jusqu'à 0014, `SCHEMA_*`, transactions IMMEDIATE), `analysis/store.rs` (lots bornés face à `serve`), `writer.rs` (écrivain unique de `serve`), `api/log_text.rs` (assainissement), `main.rs` (clap derive), fuzz xorshift de `logs/tests.rs`, vecteurs JSON de `tests/commands_vectors.rs`, job PHP 8.1 épinglé de `vigie.yml` |

### Décisions F0 appliquées ici

- Schéma **OSV 1.9.x** ; champs inconnus ignorés à la lecture (pas de `deny_unknown_fields`), validation stricte de ce qui est retenu. L'issue cite « OSV 1.6 » : F0 la remplace par 1.9.x, rétrocompatible.
- Écosystèmes : **Composer** (OSV `Packagist`), **npm**, **Cargo** (OSV `crates.io`, semver), **WordPress** et **PrestaShop** (sémantique `version_compare` de PHP). Cargo s'ajoute à la liste de l'issue (décision F0, et utile à F8).
- purl : `pkg:composer/…`, `pkg:npm/…`, `pkg:cargo/…` officiels ; `pkg:wordpress/plugin|theme/<slug>` et `pkg:wordpress/core/core` pour le noyau (proposition purl-spec #347, encore ouverte) ; `pkg:prestashop/module/<nom>` et `pkg:prestashop/core/prestashop` (convention maison, aucun type ni proposition). Ces formes remplacent les `pkg:wordpress-plugin/…` du texte de #14.
- Casse : **seul `composer` est mis en minuscules** ; `npm` et `cargo` sont sensibles à la casse et comparés tels quels.
- Traductions Packagist : `prestashop/prestashop` → `pkg:prestashop/core/prestashop` ; `prestashop/<x>` (x ≠ `prestashop`) → `pkg:prestashop/module/<x>` ; `wpackagist-plugin/<slug>` → `pkg:wordpress/plugin/<slug>` ; `wpackagist-theme/<slug>` → `pkg:wordpress/theme/<slug>`.
- Modèle OSV : plages `ECOSYSTEM` et `SEMVER` traitées, `GIT` ignorées ; entrées `withdrawn` ignorées ; `database_specific.last_known_affected_version_range` lu ; **le comparateur suit l'écosystème de la source** (une plage Packagist rattachée à `pkg:prestashop/…` passe par le comparateur Composer).
- Les `ranges` sont **toujours** évaluées ; `versions[]` sert de contrôle croisé (osv.dev#426).
- **Score de gravité**, premier présent dans cet ordre : `cvss.score` de Wordfence > score de `severity` de Friends-Of-Presta > CVSS v3.1 **calculé** depuis le vecteur OSV > `database_specific.severity` de GHSA (`CRITICAL` = 9, `HIGH` = 7, `MODERATE` = 5, `LOW` = 3). **Jamais de calcul v4.** Les entrées `MAL-` (paquet malveillant) sont repérées.
- Fixtures : enregistrements OSV/GHSA réels seulement, avec un fichier `NOTICE` (source, licence, lien, modifications) dans leur dossier ; Wordfence et Friends-Of-Presta toujours fictifs.
- Dérogations et gravité des constats viennent en F4 et F7 ; le modèle porte déjà le score retenu, son origine, les vecteurs CVSS et les alias CVE dont elles auront besoin.

Si la section F0 publiée dans `decisions.md` diffère de ces points au moment de l'implémentation, elle fait foi : corriger le plan avant de coder.

## Decisions

| Decision | Why |
| -------- | --- |
| **Aucune dépendance ajoutée.** Les comparateurs, l'analyse de purl et le calcul CVSS sont écrits ici ; les dates RFC 3339 passent par `jiff` (déjà là), les URL par `url`, le JSON par `serde_json` | Le rapprochement est le cœur de la fiabilité de la série F : il doit être lisible et testé ligne à ligne ici. Aucune crate ne reproduit `version_compare` de PHP ni la normalisation Composer, qu'il faut écrire de toute façon. Pas de nouvelle surface pour F8 (osv-scanner) ni pour le job musl |
| **Comparateur semver maison, pas la crate `semver`**, partagé par npm et Cargo (et par toute plage de type `SEMVER`) : semver 2.0 strict (pas de zéro initial dans un numérique, pas de `v`, `=`, espace ni forme partielle), préversions selon la §11, métadonnées de build **ignorées** dans l'ordre | Les événements OSV et les versions d'un lockfile sont des versions exactes, pas des exigences (`^1.2`) : seul l'ordre est nécessaire, une centaine de lignes. `semver::Version` départage aussi par les métadonnées de build (son `Ord` doit rester cohérent avec `Eq`), ce que semver 2.0 exclut de la précédence ; npm et Cargo appliquent la même précédence |
| **`version_compare` de PHP réécrit tel quel** pour WordPress et PrestaShop : canonisation (`-`, `_`, `+` → `.`, point inséré entre chiffre et lettre), puis comparaison composant par composant, ordre `dev < alpha = a < beta = b < RC = rc < # < pl = p`, composant restant comparé à `#` (`5.9 < 5.9.0`, `1.0-beta < 1.0 < 1.0pl1`) | WordPress et PrestaShop comparent ainsi ; une sémantique « plus juste » rendrait des verdicts différents de ceux du CMS |
| **Domaine accepté** : PHP compare des mots inconnus par préfixe (`bogus` vaut `b`, `patch` vaut `p`) et n'est pas transitif sur ces formes. Nos comparateurs PHP et Composer n'acceptent que les mots spéciaux exacts (insensibles à la casse seulement là où PHP l'est) ; toute autre forme est **non analysable**. Sur le domaine accepté, l'ordre est total (transitif, antisymétrique), et le test différentiel exige l'égalité avec PHP | Un ordre non transitif rend l'évaluation des plages dépendante de l'ordre de tri ; une version hors domaine finit en « version inconnue » (information en F7) au lieu d'un verdict faux |
| **Composer = normalisation Composer puis `version_compare`** : `v` initial retiré, complétée à quatre composants, stabilités `alpha|a`, `beta|b`, `RC`, `patch|pl|p`, `dev` canonisées comme `composer/semver` (`VersionParser::normalize`) ; `dev-*` et alias de branche (`1.x-dev`) **non analysables** ; versions-dates (`20260101`) admises | C'est ce que fait Composer (`Comparator` sur versions normalisées) ; les branches ne sont pas ordonnables, et osv.dev#426 vient justement de cet ordre mal implémenté |
| **Une version non analysable n'est jamais « non vulnérable »** : le rapprochement rend un verdict à trois états, `Affected`, `NotAffected`, `Unknown(raison)` ; `Unknown` pour une version d'inventaire illisible, ou une borne de plage illisible | Principe de l'issue ; F7 en fait une information « version inconnue » au lieu d'un silence |
| **Écart et indétermination distingués.** Structure contraire à OSV ou hors bornes (id, purl, dates, tailles, événement à zéro ou plusieurs clés, `fixed` et `last_affected` dans une même plage) : élément **écarté et compté** par raison, jamais fatal ; si plus aucun `affected` retenu ne reste, la faille entière est écartée et comptée. Borne de version **syntaxiquement valide mais illisible** pour notre comparateur : élément gardé, marqué `unevaluable`, rapproché en `Unknown`. Écosystème hors liste (PyPI…) : ignoré et compté à part (`out_of_scope`), ce n'est pas une erreur | Une donnée cassée ne doit pas casser la synchronisation (issue) ; une donnée que nous ne savons pas lire ne doit pas effacer une faille ; les compteurs séparés évitent qu'un dump normal (multi-écosystèmes) passe pour sale |
| **`fixed` sans `introduced`** : `introduced: "0"` ajouté. **Évaluation** : pseudo-code « Evaluation » de la spécification OSV (événements triés, `introduced`/`fixed`/`last_affected`, `limit` : affecté seulement sous une limite), recopié en commentaire et couvert par vecteurs. `versions[]` : verdict des plages ; une version listée mais hors plages reste `Affected` (sémantique d'union d'OSV) avec le drapeau `divergence` ; plages absentes ou d'un type non retenu (`GIT`) : `versions[]` seule. Appartenance par égalité du comparateur, pas par chaîne | Décision F0 « plages toujours évaluées, `versions[]` en contrôle croisé » ; l'union est la lecture prudente, le drapeau rend la divergence visible (F2 la teste sur un cas Packagist) |
| **Plage `SEMVER`** comparée au comparateur semver quel que soit l'écosystème ; **plage `ECOSYSTEM`** au comparateur de l'**écosystème de la source** (`Packagist` → Composer, `npm` et `crates.io` → semver, Wordfence → PHP, Friends-Of-Presta → PHP), stocké avec chaque `affected` (colonne `scheme`) et non déduit du type de purl : une plage Packagist sur `pkg:prestashop/module/<x>` ou `pkg:wordpress/plugin/<slug>` passe par le comparateur Composer, et la version d'inventaire est analysée avec ce même comparateur. Plages `GIT` ignorées (un `affected` qui n'a qu'elles et pas de `versions[]` est compté `out_of_scope`) | Définition des types de plage dans la spécification OSV ; la borne a été écrite dans la sémantique de sa source, la comparer autrement fausserait le verdict (décision F0 révisée) |
| **Entrées `withdrawn` ignorées à l'import** (comptées `withdrawn`, non stockées) ; une faille retirée disparaît donc à la génération suivante | Décision F0 révisée : une faille retirée ne doit produire aucun constat, et rien ne la lit ensuite |
| **`database_specific.last_known_affected_version_range`** (GHSA, forme `< v` ou `<= v`) lu, analysé avec le comparateur de la plage et gardé dans l'`affected` ; il **ne réduit pas** le verdict : une version au-delà, sans `fixed`, reste `Affected` avec le drapeau `beyond_last_known` ; une valeur illisible est ignorée et comptée | Décision F0 révisée (champ lu) ; une plage ouverte d'OSV signifie « toutes les versions suivantes », la borne connue n'est qu'une information pour F7 |
| **Paquets malveillants** : `malicious = true` pour un identifiant ou un alias `MAL-…` (OpenSSF Malicious Packages), stocké en colonne | F7 les traite à part (aucune « version corrigée » n'a de sens) ; repérage décidé en F0 |
| **Score de gravité : un seul score retenu par faille, avec son origine** (`ScoreOrigin { Wordfence, FriendsOfPresta, CvssV31, GhsaSeverity }`), premier présent dans l'ordre F0 : score fourni par Wordfence > score de Friends-Of-Presta > **CVSS v3.1 calculé ici** depuis le vecteur OSV `CVSS_V3` > `database_specific.severity` de GHSA (`CRITICAL` 9, `HIGH` 7, `MODERATE` 5, `LOW` 3). Le modèle expose `provided_score` (rempli par les convertisseurs de F3, borné à [0, 10], une décimale) ; F1 le teste avec des failles fictives construites en code. Calculateur v3.1 maison : formule de la spécification 3.1 (`Roundup` entier de l'annexe A) ; un vecteur `CVSS:3.0/` est calculé par la même formule (écart de l'arrondi seulement, noté dans les limites). **Aucun calcul v4** : un vecteur `CVSS_V4` est gardé tel quel (validé, borné) pour l'affichage. Vecteur invalide (métrique manquante, répétée ou inconnue) : entrée de gravité écartée et comptée, faille gardée. CVSS v2 et types non CVSS : ignorés ; `severity` GHSA inconnue : ignorée et comptée | Décision F0 révisée. Le score de la source CMS est celui que l'éditeur et l'utilisateur voient ; OSV ne fournit que le vecteur (`score` y est la chaîne du vecteur), d'où le calcul v3.1, court et vérifiable par les exemples de la spécification ; le calcul v4 (table de macro-vecteurs, licence de la table à vérifier) coûte trop pour un gain nul tant que GHSA publie aussi le vecteur v3.1 ou sa gravité qualitative |
| **Texte assaini par la règle de `LogText`** : `summary` = `LogText::new(brut, 500)` (constante `MAX_SUMMARY_CHARS`) ; à défaut de `summary`, première ligne de `details` assainie et bornée ; `details` jamais stocké (lien `source_url` à la place) | Une seule règle d'assainissement pour tout texte servi par l'API et la console (F7) ; un champ du type `LogText` ne peut pas porter le texte brut |
| **Références** : types `ADVISORY`, `FIX`, `WEB` seulement, URL `http`/`https` sans identifiants (`user:pass@`), 2 048 caractères au plus, 10 au plus (ordre : `ADVISORY`, `FIX`, `WEB`, puis ordre de la source) ; une référence refusée (`javascript:`, `data:`…) est retirée seule et comptée, la faille reste | Une référence est secondaire : la retirer garde la faille détectable, le compteur garde l'anomalie visible |
| **Bornes** (constantes nommées, écrites dans `failles.md`) : entrée JSON 1 Mio, identifiant et alias `[A-Za-z0-9._:-]{1,64}`, 32 alias, 64 `affected`, 16 plages par `affected`, 64 événements par plage, 10 000 `versions[]`, version 128 caractères, 8 CWE `CWE-\d{1,6}`, 4 entrées de gravité ; dates RFC 3339 stockées en secondes Unix | Les dumps sont des données tierces (hostiles par principe) ; les bornes laissent passer les plus longues énumérations Packagist observées tout en plafonnant la mémoire et la base |
| **Nom de paquet → purl** : la paire (écosystème OSV, nom) fait foi ; un `package.purl` fourni est vérifié et une divergence comptée, sans écarter. **Seul `composer` est mis en minuscules** (`vendor/name`) ; `npm` (scope `@scope` décodé en base, `%40scope` dans la forme canonique) et `cargo` sont **sensibles à la casse et comparés tels quels** ; WordPress et PrestaShop : espace de noms fermé (`plugin`, `theme`, `core` ; `module`, `core`), noyau WordPress `pkg:wordpress/core/core`, noyau PrestaShop `pkg:prestashop/core/prestashop`. Traductions Packagist, avant la règle générale `pkg:composer` : `prestashop/prestashop` → `pkg:prestashop/core/prestashop`, `prestashop/<x>` → `pkg:prestashop/module/<x>`, `wpackagist-plugin/<slug>` → `pkg:wordpress/plugin/<slug>`, `wpackagist-theme/<slug>` → `pkg:wordpress/theme/<slug>` (le comparateur reste Composer, voir « Plage »). Une table unique dans `purl.rs`, figée en vecteurs | Décisions F0 révisées ; tous les exports OSV ne portent pas de `purl` ; la clé de rapprochement doit être calculée d'une seule façon pour les inventaires (F5, F6) comme pour les failles, et une faille Packagist sur un module PrestaShop ou une extension WordPress doit tomber sur le même purl que l'inventaire de l'agent |
| **Stockage par générations** : chaque ligne de `vuln_advisories`, `vuln_aliases` et `vuln_affected` porte `(source, generation)` ; `vuln_sources.active_generation` désigne la seule génération visible. Un chargement écrit la génération suivante par lots de `VULN_BATCH` failles (transaction IMMEDIATE chacun, comme l'analyse #8), puis une transaction courte bascule `active_generation` et les compteurs ; l'ancienne génération est purgée ensuite par lots. Un chargement interrompu laisse une génération orpheline, invisible, purgée au début du chargement suivant. Toute lecture du rapprochement passe par une jointure sur `active_generation` dans une seule requête ou transaction de lecture | Remplacement atomique exigé par l'issue sans tenir le verrou d'écriture pendant tout un dump npm (≈ 208 Mio compressés) face aux écritures de `serve` ; plus simple et plus sûr que des tables d'attente renommées (pas de DDL à chaud, pas de verrou de schéma) |
| **Table `vuln_aliases`** (alias indexés) en plus du JSON d'alias demandé par l'issue | `vigie vulns show CVE-…`, la jonction CISA KEV et EPSS par CVE (F4) et la fusion des doublons au rapprochement (F7) ont besoin d'un index, impossible sur un tableau JSON |
| **Migration 0015** (dernière : 0014, registre #4) ; à l'implémentation, **prendre le prochain numéro libre** et ajuster la constante `SCHEMA_VULNS` et les tests de migration en conséquence. Seules les colonnes demandées par l'issue (plus la génération) : F2 ajoute dans sa propre migration ce dont le téléchargement a besoin (ETag, Last-Modified) | Une migration publiée ne se modifie jamais (`store.rs`) ; pas de colonne sans usage dans F1 |
| **Écrivain** : seule la synchronisation (F2, processus CLI lancé par un timer, comme `tick`) écrit ces tables, par `Store::open` ; `serve` ne fait que les lire (F7). F1 fournit l'API de chargement et la teste en contention avec l'écrivain de `serve` | Même modèle que l'analyse de logs : un processus écrit en lots, `serve` n'attend jamais plus d'un lot |
| **CLI de lecture seule**, ouverte par `Store::open_read` ; base absente ou antérieure à `SCHEMA_VULNS` : « aucune base de failles » et code 0 pour `sources`, message clair pour `show` et `match`. `vigie vulns match <purl>` sans version : toutes les failles du paquet listées « version inconnue », jamais un « aucune faille ». Aucune commande d'écriture ici (la synchronisation est `vigie vulns sync`, F2) : les tests remplissent la base par l'API de la bibliothèque | Périmètre de l'issue ; `match` est l'outil de vérification à la main et de test de bout en bout |
| **Fixtures** : enregistrements réels **OSV/GHSA seulement** (une GHSA Composer et une GHSA npm, CC-BY 4.0 ; une RUSTSEC, CC0), choisis à l'implémentation sur des paquets publics sans lien avec un client, accompagnés d'un fichier `NOTICE` dans leur dossier (`tests/fixtures/vulns/osv/NOTICE` : pour chaque fichier, source, licence, lien vers l'enregistrement, modifications apportées ou « aucune ») ; tout ce qui imite Wordfence ou Friends-Of-Presta est **fictif** (`pkg:wordpress/plugin/exemple-plugin`, `pkg:prestashop/module/exemplemodule`, URL `https://example.org/…`), de même que les cas Composer inventés (`exemple/paquet`) ; une fixture hostile par raison d'écart | Critère d'acceptation de l'issue ; décision F0 révisée (attribution au plus près des données) ; règle « dépôt public » (aucune donnée de production, aucun inventaire client) |
| **Test différentiel PHP** : `tests/vulns_php_diff.rs`, ignoré par défaut, **échoue au lieu d'être sauté** quand `VIGIE_PHP` est posé (même convention que `VIGIE_E2E_PHP`) ; nouveau pas du job Linux de `vigie.yml` avec la même image `php:8.1-cli` épinglée par digest. Il couvre `version_compare` (WordPress, PrestaShop) et l'étape de comparaison de Composer sur versions déjà normalisées ; la normalisation Composer est couverte par des vecteurs repris de `VersionParserTest` de `composer/semver` (MIT, cité), Composer n'étant pas dans l'image | L'issue demande le différentiel « optionnel » ; la CI a déjà PHP 8.1 ; sans PHP local, le test ne bloque pas un poste Windows |
